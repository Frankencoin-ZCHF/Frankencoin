## Findings

### [L-01] Misleading NatSpec deployment step  *(Low)*

**Location:** `ZCHFTransferWithAuthorization.sol:16`

**Description:** The NatSpec deployment guide states:

```
2. Fund the application fee: ZCHF.transfer(deployer, ZCHF.MIN_FEE()).
```

`ZCHF.transfer(deployer, ...)` is a self-transfer from the deployer to themselves — a no-op that wastes gas and does nothing. A deployer following these instructions literally would not understand why step 3 (`suggestMinter`) then reverts due to insufficient balance.

The intent is simply that the deployer must *hold* at least `ZCHF.MIN_FEE()` ZCHF before calling `suggestMinter`, which debits the fee directly from `msg.sender`.

**Recommendation:** Replace step 2 with:

```
2. Ensure the deployer holds at least ZCHF.MIN_FEE() in ZCHF.
   suggestMinter() will transfer this amount from msg.sender to the reserve.
```

### [L-02] No explicit minter-liveness guard  *(Low)*

**Location:** `ZCHFTransferWithAuthorization.sol:94`, `121`

**Description:** If this contract has not yet been approved as a minter (e.g. still within the application period, or governance voted to deny it), calls to `transferWithAuthorization` and `receiveWithAuthorization` revert with `ERC20InsufficientAllowance` from deep inside the Frankencoin token contract. This is technically correct (the transfer fails safely), but the error is opaque — callers see an allowance error on a contract that never required an approval, which is confusing to debug.

**Recommendation:** Add a preflight check at the top of both transfer functions:

```solidity
if (!ZCHF.isMinter(address(this))) revert NotApprovedAsMinter();
```

This surfaces the real reason for failure and protects integrators from misdiagnosing the error as a ZCHF token bug.

### [I-01] Immutable `DOMAIN_SEPARATOR` does not update on chain fork  *(Info)*

**Location:** `ZCHFTransferWithAuthorization.sol:53–62`

**Description:** `DOMAIN_SEPARATOR` is computed once in the constructor using `block.chainid` and stored as an `immutable`. If the chain later forks and changes its chain ID (e.g. an emergency hard fork), the separator becomes stale. Authorizations signed before the fork would be valid on both resulting chains.

This is consistent with how `ERC20PermitLight` handles the domain separator in this same repo, and is the standard approach used by USDC (Circle's EIP-3009 reference implementation). The risk is low in practice.

**Recommendation:** No action required unless the project explicitly needs to handle fork scenarios. Document the design decision for future auditors.

### [I-02] `verifyingContract` resolves to the sidecar, not the ZCHF token  *(Info)*

**Location:** `ZCHFTransferWithAuthorization.sol:59`

**Description:** The EIP-712 domain `verifyingContract` is `address(this)` — the sidecar contract — not the ZCHF token address. Wallet UIs that render the signing domain (MetaMask, Ledger Live) will display the sidecar's address and name "Frankencoin", which may be unfamiliar to users who only know the ZCHF token address. This is architecturally correct (the sidecar is the contract enforcing the message), but could confuse users who expect to sign against the token they see in their wallet.

**Recommendation:** Off-chain relayer UIs and integrators should clearly display that the user is authorizing the `ZCHFTransferWithAuthorization` sidecar contract. Consider adding `ZCHF` as a public getter on the sidecar so dApps can display the underlying token address alongside the signing domain.

---

### [I-03] Minter privilege scope is broader than minimum required  *(Info)*

**Location:** Frankencoin minter architecture (external)

**Description:** Once approved as a minter, this contract holds implicit infinite allowance over every ZCHF balance *and* the right to call `mint()`, `burnFrom()`, `mintWithReserve()`, and related functions directly on the Frankencoin contract. The sidecar has no code paths that invoke those functions, so the additional surface is inert in the current bytecode.

However, if the bytecode were different from the audited source (build artifact mismatch, supply chain), those functions would be exploitable. Similarly, if this contract were ever mistakenly used as a proxy base, the privilege could be abused.

**Recommendation:** Verify the deployed bytecode hash against the audited source before governance approval. Consider adding a `bytes32 public constant BYTECODE_HASH` constant in the contract to facilitate on-chain verification. Document that minter status for this contract should be treated as permanent — Frankencoin has no minter revocation path after the application period.

## Notes

**Reentrancy:** All three public functions follow Checks-Effects-Interactions strictly. The nonce is marked consumed (`_markUsed`) before the external `ZCHF.transferFrom` call. No reentrancy risk.

**Signature malleability:** `ecrecover` with high-`s` values can produce a second valid `(v, r, s)` for the same message. This is harmless here because both forms recover to the same address and consume the same nonce — the second submission would revert with `AuthorizationAlreadyUsed`.

**Unchecked `transferFrom` return value:** `ZCHF.transferFrom` always reverts on failure (per `ERC20.sol`: "functions revert instead of returning false"). The unchecked return is safe for ZCHF specifically.

**Type hash correctness:** All three EIP-3009 type hashes and the EIP-712 domain type hash were verified against the canonical values from the EIP specification. All match.

**Timestamp boundary conditions:** `block.timestamp <= validAfter` (revert if at or before) and `block.timestamp >= validBefore` (revert if at or after) match EIP-3009 semantics exactly.

**`cancelAuthorization` access:** Only the authorizer can produce a valid cancel signature. A third party who observes a cancel transaction in the mempool can front-run its submission, but the outcome (nonce permanently blocked) is the authorizer's intended effect — this is not exploitable.
